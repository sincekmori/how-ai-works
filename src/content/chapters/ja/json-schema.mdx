前の章までで、JSON という形を手に入れ、モデルにその形で返させたい、という狙いが定まりました。
では、どうやって JSON で返させるのでしょう。
いちばん素朴なのは、プロンプト（お願いの文）でそう頼むことです。

## 「JSON で返して」と頼んでみる

たとえば、こうお願いします。

> 東京の明日の天気を、`{ "city": ..., "condition": ..., "temperature": ... }` の JSON で答えて。

かんたんな形なら、モデルはたいてい応じてくれます。
下のデモで「決まった型で答えさせる（JSON）」を選ぶと、その様子が見られます。

<StructuredToggle client:visible />

うまくいくなら、これで解決……と言いたいところですが、そう甘くありません。
モデルは第 1 部で見たとおり、1 語ずつ「それっぽさ」で選ぶ機械。
「JSON で返して」はあくまで **お願い** であって、**保証** ではありません。
だから、こんなふうに綻びます。

## お願いだけでは、綻びる

**綻び 1：前置きがつく。**
モデルは親切なので、つい前置きを添えます。

```text
はい、承知しました。東京の明日の天気はこちらです：
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```

先頭の文が JSON ではないので、そのままではプログラムが読めません。

**綻び 2：囲みがつく。**
文章の中でコードを見せるときの習慣で、こんな囲みが入ることもあります。

````text
```json
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```
````

**綻び 3：構造がずれる。**
`temperature`（数値）のつもりが `"28度"`（文字列）で返ってきたり、頼んでいない鍵が増えたり、鍵の名前が微妙に違ったり。

「じゃあ、囲みの中身を正規表現で抜けばいい」と思うかもしれません。
でも、前の章のモグラたたきを思い出してください。
囲みが **必ずある保証はない** し、あっても中の構造がずれていたら、けっきょく読めません。
お願いベースでは、いつまでも「たぶん大丈夫」の域を出られないのです。

## 形そのものを、定義する

そこで、発想をもう一段あげます。
「こんな感じで返してね」と例で示すのは、記入例を見せるようなもの。
そうではなく、**記入欄が最初から決まっている用紙** を渡すのです。

その用紙の決まりごとを、ことばで書き出すと、こうなります。

- 鍵は `city`・`condition`・`temperature` の 3 つ
- `city` と `condition` の値は文字列
- `temperature` の値は数値
- 3 つの鍵は、必ず全部そろえること

ここで、問題がひとつ。
この決まりごとを日本語のメモで渡しても、機械のしくみには読ませられません。
決まりごと **自体も**、決まった形で書く必要があるのです。

では、どんな形で書きましょう。
上の決まりごとをよく見ると、「`city` という鍵の値は、文字列という種類」のように、**決まりごと自体が「鍵と値」のペア** でできています。
鍵と値を書くのにぴったりの形を、私たちはもう知っていますよね。
そう、JSON です。
つまり、**JSON がどう書かれるべきかのルールを、JSON そのもので書く**。
このルールの書き方の世界標準が **JSON スキーマ（JSON Schema）** です。
スキーマとは「型（かた）の設計図」のこと。
さっきの天気の決まりごとを、JSON スキーマで書くと、こうなります。

```json
{
  "type": "object",
  "properties": {
    "city": { "type": "string" },
    "condition": { "type": "string" },
    "temperature": { "type": "number" }
  },
  "required": ["city", "condition", "temperature"]
}
```

読み方は、前の章の「鍵をたどる」でそのまま通じます。
`"type": "object"` は「全体は `{ }` のかたまり」。
`"properties"` の中が「どんな鍵があって、それぞれの値がどんな種類か」。
`temperature` は `"type": "number"`、つまり **数値でなければならない**（`"28度"` のような文字列はダメ）。
`"required"` は「この鍵は必ず入れること」。
これは「例」ではなく **ルール** です。
「だいたいこんな感じ」ではなく、「この形以外は認めない」と宣言しているのです。

## なぜ、必ず守られるのか

スキーマを渡すと、モデルは形を **必ず** 守れます。
お願いのときは綻んだのに、なぜ今度は保証できるのでしょう。
からくりは、推論の章で見た「次の 1 語の選び方」にあります。

思い出してください。
モデルは毎回、候補ぜんぶに割合（確率）をつけていました。
そして、その中から 1 つ選んで書き足していました。
スキーマがあるときは、この割合表に **フィルタ** をかけます。
「いまスキーマ上、次に来てよい文字はこれだけ」という許可リストを作り、それ以外の候補の割合を **0 にしてしまう** のです。

たとえば `{ "city":` まで書けた場面。
スキーマ上、次は文字列の値、つまり引用符 `"` が来るべきところ。
だから「`"` 以外は選べない」と締めつける。
`temperature` の値を書く場面なら、数字しか選べないようにする（`"` は禁止）。
こうして、**選べる手を、つねに形に沿ったものだけに限る**。
モデルは前置きも囲みもはさめず、鍵をまちがえることもできません。
お願いで導くのではなく、**通り道そのものを、スキーマの形にくり抜く**。
だから「必ず」守られるのです。
この、決まった形での出力を **構造化出力（Structured Output）** と呼び、JSON スキーマはその「形の指定」を担います。

## これで、部品になる

ふり返れば、長い道のりでした。
自由な文から正規表現で抜こうとして、モグラたたきに疲れ、JSON で返させる発想にたどり着き、お願いだけでは綻ぶと知り、ついに **形そのものを定義して保証する** ところまで来ました。
これで、モデルの返事は、ぶれない **決まった型のデータ** になります。
決まった型なら、プログラムがそのまま読み取り、次の処理へ渡せる。
天気の JSON を絵にする、点数で合否を判定する、住所を地図 API に渡す。
モデルは「おしゃべり相手」から、**アプリの中で他の部品とつながる部品** になったのです。

そして次の章では、この流れを逆向きにも使います。
モデル自身が「この道具を、この値で使って」と、構造化出力で **お願いしてくる** ようにするのです。
モデルに、外の世界の道具を持たせましょう。
