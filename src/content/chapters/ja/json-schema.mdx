JSON という形は手に入りました。
あとは、モデルにその形で返してもらうだけです。
いちばん素朴な方法は、プロンプト（モデルに渡す指示の文章）でそう頼むことです。

## 「JSON で返して」と頼んでみる

たとえば、こうお願いします。

> 東京の明日の天気を、`{ "city": ..., "condition": ..., "temperature": ... }` の JSON で答えて。

かんたんな形なら、モデルはたいてい応じてくれます。
下のデモで「決まった型で答えさせる（JSON）」を選ぶと、その様子が見られます。

<StructuredToggle client:visible />

これで解決、と言いたいところですが、そう甘くありません。
モデルは第 I 部で見たとおり、1 語ずつ「それっぽさ」で選ぶ機械です。
「JSON で返して」はあくまでお願いであって、保証ではありません。
実際、次のように綻びます。

## お願いだけでは、綻びる

1 つめは、前置きです。
モデルは親切なので、つい前置きを添えます。

```text
はい、承知しました。東京の明日の天気はこちらです：
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```

先頭の文が JSON ではないので、そのままではプログラムが読めません。

2 つめは、囲いです。
文章の中でコードを見せるときの習慣で、こんな囲みが入ることがあります。

````text
```json
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```
````

3 つめは、構造のずれです。
`temperature`（数値）のつもりが `"28度"`（文字列）で返ってきたり、頼んでいない鍵が増えたり、鍵の名前が微妙に違ったりします。

囲みの中身を正規表現で抜けばいい、と思うかもしれません。
しかし、前の章のモグラたたきを思い出してください。
囲みが必ずあるという保証はありませんし、あっても中の構造がずれていれば、けっきょく読めません。
お願いベースでは、いつまでも「たぶん大丈夫」の域を出られないのです。

## 形そのものを、定義する

そこで、発想をもう一段あげます。
「こんな感じで返してね」と例で示すのは、記入例を見せるようなものでした。
そうではなく、記入欄が最初から決まっている用紙を渡します。

その用紙の決まりごとを、ことばで書き出すと、こうなります。

- 鍵は `city`、`condition`、`temperature` の 3 つ
- `city` と `condition` の値は文字列
- `temperature` の値は数値
- 3 つの鍵は、必ず全部そろえること

ここで、問題がひとつあります。
この決まりごとを日本語のメモで渡しても、機械のしくみには読ませられません。
決まりごと自体も、決まった形で書く必要があります。

どんな形で書きましょうか。
上の決まりごとをよく見ると、「`city` という鍵の値は、文字列という種類」のように、決まりごと自体が鍵と値のペアでできています。
鍵と値を書くのにぴったりの形を、私たちはもう知っています。
JSON です。
つまり、JSON がどう書かれるべきかのルールを、JSON そのもので書く。
このルールの書き方の世界標準が **JSON スキーマ**（JSON Schema）です。
スキーマとは、型の設計図のことです。
さっきの天気の決まりごとを JSON スキーマで書くと、こうなります。

```json
{
  "type": "object",
  "properties": {
    "city": { "type": "string" },
    "condition": { "type": "string" },
    "temperature": { "type": "number" }
  },
  "required": ["city", "condition", "temperature"]
}
```

読み方は、前の章の「鍵をたどる」がそのまま通じます。
`"type": "object"` は「全体は `{ }` のかたまり」。
`"properties"` の中が「どんな鍵があって、それぞれの値がどんな種類か」。
`temperature` は `"type": "number"`、つまり数値でなければなりません（`"28度"` のような文字列は認められません）。
`"required"` は「この鍵は必ず入れること」。
これは例ではなくルールです。
「だいたいこんな感じ」ではなく、「この形以外は認めない」と宣言しています。

## なぜ、必ず守られるのか

この締めつけを実際に行うしくみを通してスキーマを渡すと、モデルは形を必ず守れます。
お願いのときは綻んだのに、なぜ今度は保証できるのでしょうか。
からくりは、推論の章で見た「次の 1 語の選び方」にあります。

モデルは毎回、候補ぜんぶに確率をつけて、その中から 1 つ選んで書き足すのでした。
スキーマがあるときは、この割りふり表にフィルタをかけます。
「いまスキーマ上、次に来てよい部品（トークン）はこれだけ」という許可リストを作り、それ以外の候補の確率を 0 にしてしまうのです。

たとえば `{ "city":` まで書けた場面を考えます。
スキーマ上、次は文字列の値、つまり引用符 `"` が来るべきところです。
だから「`"` 以外は選べない」と締めつけます。
`temperature` の値を書く場面なら、数字しか選べないようにします。
モデルは前置きも囲みもはさめず、鍵をまちがえることもできません。
お願いで導くのではなく、通り道そのものをスキーマの形にくり抜く。
だから「必ず」なのです。
この、決まった形での出力を **構造化出力**（Structured Output）と呼び、JSON スキーマはその形の指定を担います。
なお、「必ず」には注釈が 2 つあります。
保証が効くのは、この締めつけを実際に行うモード（構造化出力）で呼んだときです。
また、パラメータの章の max_tokens の上限に当たれば、正しい形の途中でもぷつりと切れることはありえます。

## これで、部品になる

ふり返れば、長い道のりでした。
自由な文から正規表現で抜こうとしてモグラたたきに疲れ、JSON で返させる発想にたどり着き、お願いだけでは綻ぶと知り、形そのものを定義して保証するところまで来ました。
モデルの返事は、これでぶれない決まった型のデータになります。
決まった型なら、プログラムがそのまま読み取り、次の処理へ渡せます。
天気の JSON を絵にする、点数で合否を判定する、住所を地図の窓口に渡す。
モデルは、おしゃべり相手から、アプリの中で他の部品とつながる部品になりました。

ところで、この「決まった型のやりとり」には、逆向きの使い道があります。
モデルのほうから「この道具を、この値で使いたい」と、決まった型でお願いしてくるとしたら、どうでしょうか。
