アプリの中でモデルの返事を受け取るのはプログラムで、プログラムは自由な文章がいちばん苦手なのでした。
では、どれくらい苦手なのでしょうか。
手を動かして確かめてみます。

## まず、素朴にやってみる

モデルがこう返してきたとします。

> 東京は明日、28 度まで上がるでしょう。

そもそも、なぜ数字を取り出したいのでしょうか。
たとえば、明日の気温が 30 度を超えそうなら、朝のうちに「熱中症に注意。水分をこまめに」と通知するアプリを作っているとします。
通知を出すかどうかを決めるには、プログラムが「明日の気温は 30 より大きいか」という数の比較をする必要があります。
「28 度まで上がるでしょう」という文章のままでは、30 と比べられません。
比べられるのは数字そのものです。
だから、この返事から気温の数字（28）だけを取り出したいわけです。

プログラムは文の意味こそ分かりませんが、文字の並びを手がかりに探すことならできます。
数字の並びを探すようなパターン検索は、**正規表現** という道具でできます。
「こういう形の文字列を探して」と指示するための、小さな書き方です。
たとえば `\d` は「数字 1 文字」、`\d+` は「数字が 1 文字以上つづく並び」を表します。
記号の読み書きをここで覚える必要はありません。
文字のパターンを指定して探す道具がある、と分かれば、この章はぜんぶ読めます。

さっきの文なら、`\d+` で「28」が取れます。
うまくいきました。
本当でしょうか。

## 言い回しが変わると、崩れていく

問題は、モデルの返事が毎回おなじ言い回しとは限らないことです。
下のデモで正規表現を選んで、3 つの文それぞれで何が取れるかを見てみてください。

<RegexTrap client:visible />

やってみると、こうなったはずです。

- `\d+`（最初の数字）は、「3 日の東京は、28 度まで上がる」で日付の 3 を取ってしまう。
- それならと `\d\d度まで` にすると、日付は避けられる。ところが「気温は 28 度です」という言い方には「まで」がないので一致しない。
- それならと `気温は\d\d度` を足すと、今度は「28 度まで上がる」の文が拾えない。

どのパターンを選んでも、3 つの文ぜんぶでは正解できません。
言い回しを 1 つ思いつくたびに、正規表現をつぎ足すことになります。
「朝は 15 度、昼は 28 度」なら？
「28℃」と書き方が違ったら？
「二十八度」と漢数字だったら？
きりがありません。
終わりのないモグラたたきです。

## 発想を変える

ここで、気づいてほしいことがあります。
私たちはずっと、すでに書かれてしまった自由な文から、あとで情報を取り出そうとしていました。
だから、無数の言い回しを追いかけるはめになったのです。

逆にしたらどうでしょうか。
取り出しやすい形で、最初から書いてもらう。
モデルへのお願いを「文章で答えて」から「この形で答えて」に変えるのです。
そういう取り出しやすい形は、すでに世界中で使われています。
名前を **JSON** といいます。

もし返事が

```json
{ "temperature": 28 }
```

だったら、もうモグラたたきは要りません。
`temperature` という鍵の値を取るだけで、いつでも確実に 28 が手に入ります。
言い回しは無数でも、形はひとつに決められる。

では、その JSON とは、どんな形をしているのでしょうか。
