この部のはじめの章で、アプリの中では、モデルの返事を受け取るのが **プログラム** だと分かりました。
そして、プログラムは自由な文章がいちばん苦手だ、とも。
でも、どれくらい苦手なのでしょう。
その大変さを、実際に手を動かして確かめます。
この大変さこそが、これから出てくる大事な発想の、出発点になります。

## まず、素朴にやってみる

モデルがこう返してきたとします。

> 東京は明日、28 度まで上がるでしょう。

なぜ、わざわざ数字を取り出したいのでしょう。
たとえば、こんなアプリを作っているとしましょう。
明日の気温が 30 度を超えそうなら、朝のうちに「熱中症に注意。水分をこまめに」と通知するアプリです。
通知を出すかどうかを決めるには、プログラムが「明日の気温は 30 より大きいか？」という **数の比較** をする必要があります。
「28 度まで上がるでしょう」という文章のままでは、30 と比べられません。
比べられるのは、数字そのもの。
だから、この返事から **気温の数字（28）** だけを取り出したいのです。
プログラムは文の意味こそ分かりませんが、文字の並びを手がかりに「探す」ことならできます。
「数字の並びを探す」というパターン検索は、**正規表現** という道具でできます。
正規表現は「こういう形の文字列を探して」と指示するための、小さな書き方です。
たとえば `\d` は「数字 1 文字」、`\d+` は「数字が 1 文字以上つづく並び」を表します。
この記号の読み書きを、ここで覚える必要はまったくありません。
「文字のパターンを指定して探す、こういう道具があるんだな」と分かれば、この章はぜんぶ読めます。

さっきの文なら、`\d+` で「28」が取れます。
うまくいきました。
……本当に？

## 言い回しが変わると、崩れていく

問題は、モデルの返事が **毎回おなじ言い回しとは限らない** ことです。
下のデモで、正規表現を選んで、3 つの文それぞれで何が取れるかを見てみてください。

<RegexTrap client:visible />

やってみると、こうなったはずです。

- `\d+`（最初の数字）は、「3 日の東京は、28 度まで上がる」で **日付の 3** を取ってしまう。
- じゃあと `\d\d度まで` にすると、日付は避けられる。でも「気温は 28 度です」という言い方には「まで」がないので **一致しない**。
- じゃあと `気温は\d\d度` を足すと、今度は「28 度まで上がる」の文が拾えない。

**どのパターンを選んでも、3 つの文ぜんぶでは正解できません。**
言い回しを 1 つ思いつくたびに、正規表現をつぎ足すことになります。
「朝は 15 度、昼は 28 度」なら？　「28℃」と単位が違ったら？　「二十八度」と漢数字だったら？
きりがありません。
これは、終わりのない **モグラたたき** です。

## 発想を変える

ここで、大事な気づきがあります。
私たちはずっと、**すでに書かれてしまった自由な文** から、あとで情報を取り出そうとしていました。
だから、無数の言い回しを追いかけるはめになったのです。

では、逆にしたらどうでしょう。
**取り出しやすい形で、最初から書いてもらう。**
モデルに「文章で答えて」ではなく、「この形で答えて」とお願いするのです。
じつは、そういう「取り出しやすい形」は、すでに世界中で使われています。
その名を **JSON** といいます。

もし返事が

```json
{ "temperature": 28 }
```

だったら、もうモグラたたきは要りません。
`temperature` という鍵の値を取るだけで、いつでも確実に 28 が手に入ります。
言い回しは無数でも、**形はひとつ** に決められるのです。

では、その JSON とは、いったいどんな形なのでしょう。
次の章で、正体をちゃんと見ていきます。
