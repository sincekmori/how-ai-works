モデルに決まった型で答えさせられるようになりました。
この力は、意外な方向にも使えます。
モデルに、外の世界の道具を持たせるのです。

## モデル単体の限界

どんなに賢いモデルにも、できないことがあります。
モデルが知っているのは、学習した時点までの、世の中の文章から学んだことだけです。
だから今日の天気や今の株価は知りません。
それに、モデルの中身は結局、確率で次の 1 語を選ぶ仕掛けでした。
桁の多い掛け算を、電卓のように正確に計算するのは苦手です。

これらは、モデルを賢くすれば消える弱点ではありません。
最新情報は、そもそもモデルの中にないのです。
必要なのは頭を良くすることではなく、外の道具を使わせることです。
天気を知りたければ天気サービスに聞き、計算したければ電卓を叩く。
人間も、そうしています。

## それでも、モデルは道具を動かせない

ここで問題があります。
モデルにできるのは、結局、言葉（トークン）を出すことだけです。
天気サービスを自分でネット越しに呼んだり、電卓を自分で操作したりはできません。

そこで、前の章の構造化出力が効いてきます。
モデルは道具を自分で動かす代わりに、「この道具を、この値で呼んで」という依頼を、決まった型で書き出すのです。
例えば天気を知りたい場面では、こんな形を出します。

```json
{ "tool": "get_weather", "city": "Tokyo", "when": "tomorrow" }
```

これは前章の構造化出力そのものです。
決まった型なので、間にいるプログラムが確実に読み取れます。
読み取ったプログラムが実際に天気サービスを呼び、結果をモデルに戻す。
モデルは、その結果を見て最後の返事を作る。
この一周が **ツール** の利用です（**関数呼び出し**、function calling とも呼ばれます）。

## 登場人物が、三人になった

この本に出てきた会話は、ここまでずっと二人のものでした。
あなた（またはプログラム）が聞き、モデルが答える。
どんなに長いやり取りでも、お願いと返事が往復するだけの世界でした。

ツールが入ったいま、会話の輪に第三の登場人物が加わっています。
天気サービス、電卓、検索。
モデルでもあなたでもない道具が、やり取りの一員になったのです。

ただし、道具は言葉を話しません。
モデルと道具は、直接には会話できないのです。
間に立つプログラムが取り次ぎ役になります。
モデルの「この道具を呼んで」を道具に伝え、道具の返した結果をモデルに届ける。
三人の会話は、いつも真ん中のプログラムを経由して進みます。

モデルの発言にも、2 種類が生まれました。
人に向けた言葉と、道具に向けた依頼です。
あなたの画面には、最後の返事しか映りません。
しかし裏側の会話の記録には、あなたが見たことのない行、つまり道具への依頼と道具からの結果が、静かに挟まっています。

## 一周を、歩いてみる

言葉だけでは分かりにくいので、1 歩ずつ追ってみます。

<ToolLoop client:visible />

大事なのは役割分担です。
モデルは「何を、どの道具で調べるか」を決めるだけ。
実際に道具を動かすのは、間のプログラムです。
モデルは結果を受け取って、人向けの返事に仕上げます。
考える人と手を動かす人を分けている、ととらえると分かりやすいはずです。

道具は天気サービスだけではありません。
ウェブ検索、電卓、コードの実行、社内の予定表、データベース。
決まった型で呼べて結果が返ってくるものなら、何でも道具にできます。
あなたが普段使っているアシスタントの多くも、裏でこうして道具を呼んでいます。

## 道具が増えると、どうなるか

道具を持たせられると分かると、欲が出ます。
天気も、検索も、地図も、カレンダーも使わせたい。
ところが、道具を一つ足すたびに「この道具はこう呼ぶ」という取り決めを手作業で繋いでいくと、すぐに立ちゆかなくなります。
モデルもたくさん、道具もたくさん。
その全部の組み合わせを手配線していたら、配線だらけです。
この配線問題には、すでに答えが用意されています。
道具の世界の、共通のコンセントです。
