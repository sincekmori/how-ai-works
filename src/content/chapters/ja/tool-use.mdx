前の章で、モデルに決まった型で答えさせられるようになりました。
この章では、その力を意外な方向に使います。
モデルに、**外の世界の道具** を持たせるのです。

## モデル単体の限界

どんなに賢いモデルにも、できないことがあります。
モデルが知っているのは、学習したときまでの、世の中の文章から学んだことだけ。
だから **今日の天気** や **今の株価** は知りません。
それに、第 1 部で見たとおり、モデルは 1 語ずつ「それっぽさ」で言葉を選ぶ機械。
桁の多いかけ算を、電卓のように **正確に** 計算するのは苦手です。

これらは、モデルを賢くすれば消える弱点ではありません。
最新情報は、そもそもモデルの中にないのです。
必要なのは、頭を良くすることではなく、**外の道具を使わせる** ことです。
天気を知りたければ天気サービスに聞き、計算したければ電卓を叩く。
人間だってそうしていますよね。

## でも、モデルは道具を動かせない

ここで問題があります。
モデルにできるのは、結局 **言葉（トークン）を出すこと** だけ。
天気 API を自分でネット越しに叩いたり、電卓を自分で操作したりはできません。

そこで、前の章の構造化出力が効いてきます。
モデルは道具を **自分で動かすのではなく**、「この道具を、この値で呼んで」という **依頼を、決まった型で書き出す** のです。
たとえば天気を知りたい場面では、こんな形を出します。

```json
{ "tool": "get_weather", "city": "Tokyo", "when": "tomorrow" }
```

これは、まさに前章の構造化出力そのもの。
決まった型なので、あいだにいるプログラムが確実に読み取れます。
読み取ったプログラムが、実際に天気 API を叩き、結果をモデルに戻す。
モデルは、その結果を見て最後の返事を作る。
この一周が、**ツール（道具）の利用**、別名 **関数呼び出し（function calling）** です。

## 登場人物が、3 人になった

ここで、少し立ち止まってください。
いま、静かに、でもとても大きな変化が起きました。

この本に出てきた会話は、ここまでずっと **2 人** のものでした。
あなた（またはプログラム）が聞き、モデルが答える。
どんなに長いやりとりでも、登場人物はこの 2 人だけ。
「お願い」と「返事」が往復するだけの世界でした。

ツールが入ったいま、会話の輪に **第三の登場人物** が加わっています。
天気サービス、電卓、検索。
モデルでもあなたでもない「道具」が、やりとりの一員になったのです。

ただし、道具は言葉を話しません。
だからモデルと道具は、直接には会話できません。
あいだに立つプログラムが **取り次ぎ役** になります。
モデルの「この道具を呼んで」を道具に伝え、道具の返した結果をモデルに届ける。
3 人の会話は、いつも真ん中のプログラムを経由して進みます。

モデルの発言にも、2 種類が生まれました。
**人に向けた言葉** と、**道具に向けた依頼** です。
あなたの画面には最後の返事しか映りません。
でも裏側の会話の記録には、あなたが見たことのない行、つまり道具への依頼と道具からの結果が、静かに挟まっているのです。

## 一周を、歩いてみる

言葉だけだと分かりにくいので、実際に 1 歩ずつ追ってみましょう。

<ToolLoop client:visible />

大事なのは、役割分担です。
**モデルは「何を、どの道具で調べるか」を決めるだけ。**
**実際に道具を動かすのは、あいだのプログラム。**
モデルは結果を受け取って、人向けの返事に仕上げます。
「考える人」と「手を動かす人」を分けている、と思うと分かりやすいでしょう。

道具は天気 API だけではありません。
ウェブ検索、電卓、コードの実行、社内の予定表、データベース。
「決まった型で呼べて、結果が返ってくる」ものなら、何でも道具にできます。
あなたがふだん使っているアシスタントの多くも、裏でこうして道具を呼んでいます。

## 次の問題：道具が増えると

道具を持たせられると分かると、欲が出ます。
天気も、検索も、地図も、カレンダーも、あれもこれも使わせたい。
ところが、道具を 1 つ足すたびに「この道具はこう呼ぶ」という取り決めを、モデルとプログラムの間で手作業でつないでいくと、すぐに大変なことになります。
モデルもたくさん、道具もたくさん。
その全部の組み合わせを手配線していたら、配線だらけです。

次の章では、この「道具のつなぎ方」を標準化するしくみ、**MCP** を見ます。
道具の世界に、共通のコンセントを用意する話です。
