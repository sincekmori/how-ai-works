The previous chapter ended on an ominous note: as tools multiply, you drown in wiring.
This chapter is about what that dead end really is — and the standard that leads out of it, **MCP**.

## What does "connecting" actually involve?

First, make concrete what "connecting a model and a tool" means.
When the weather tool was used last chapter, this much preparation was happening backstage.

One: teach the description.
"There is a tool called get_weather; give it a city and a date and it returns the weather" — the tool's name, abilities, and input shape must be told to the model at every conversation.
Without the description, the model doesn't even know the tool exists.
Two: write the go-between program —
the part that reads the model's tool call, translates it into the real weather service's calling convention, calls it, and hands the result back to the model.
Three: repeat both, per tool.

Laborious, but with one tool and one model, bearable.

## Hand-wiring grows by multiplication

Reality multiplies quickly, though.
There are many kinds of models (GPT, Llama, Claude, Gemini…).
And the fine shape of "how tool calls are written" differs a little from model to model.
Nor do tools stop at weather (search, maps, calendars…).

Say you have painstakingly wired the weather tool to one model.
It works.
Then a friend says, "I want that weather tool in my app too."
But the friend's app is built on a different model.
The description is passed differently, the tool-call shape differs — same tool, full rewiring.
Another friend uses yet another model… and the wires multiply while the number of tools stays exactly the same.

What if everything were connected directly?
With M kinds of models and N kinds of tools, you need M × N connection agreements.
Add one model: new wiring for every tool.
Add one tool: new wiring for every model.
It gets out of hand fast.

## Put a common socket in between

There is a better way.
Stop connecting models and tools directly; place one common agreement in between.
Declare: a tool describes itself in this common shape, and is called in this common shape.
Then each app carrying a model only needs to speak that one shape, and each tool only needs to be offered in it.
Everyone plugs into the common socket, and that is all.

That common-socket agreement is **MCP** (Model Context Protocol).
Think USB-C.
Chargers used to come in a different shape per device; once USB-C became the common shape, one cable fits many devices.
MCP is USB-C for the world of tools.

## Where did the wiring work go?

In the MCP world, the three preparations transform.

First, a tool is packaged in a common wrapper called an **MCP server**.
The server's most important trick: asked, it describes itself.
"I am a tool called get_weather. I take a city and a date, and return the weather" — name, abilities, input shape, all in the common form.
The human chore of hand-writing descriptions per model is gone.

Second, the app prepares a single receptacle called an **MCP client**, once.
It is the common version of the go-between program.
Built once, it converses by the same procedure with whatever tool gets plugged in.

Adding a new tool then becomes exactly plugging one more plug into the socket.
The app asks the plugged-in tool "what can you do?", and shows the returned description straight to the model.
The model writes its tool call — "use this tool with these values" — in precisely the manner of the previous chapter.
No hand-written descriptions, no per-tool go-betweens, no rewiring.

## How much easier does it get?

"Common shapes make life easier" may not land by itself.
Look at the numbers.
Move the sliders below — number of models, number of tools.

<McpPlug lang="en" client:visible />

Hand-wiring grows by multiplication (M × N); MCP grows by addition (M + N).
At small numbers, little difference.
As they grow, multiplication balloons while addition ambles.
Push both sliders to the far right — 8 and 8 — and it is 64 wires by hand, 16 with MCP.
That gap is what matters in a world where tools keep multiplying.
A tool that speaks MCP once is usable from any app that speaks MCP, whichever model that app runs.
And a toolmaker prepares one MCP-shaped package, without worrying about per-model support.

## Standards pay off for everyone

The important thing: MCP is not any single company's property.
A common agreement is valuable precisely because everyone uses the same one.
And indeed MCP is a published specification, with a growing range of apps and tools supporting it.
Set against this part's through-line, its place is clear.
Just as structured output fixed the shape of replies to one and gave programs peace of mind, MCP fixes the way tools are connected to one — and extends the same peace of mind to a much wider circle.

The parts are now assembled.
Answers in fixed shapes; tools in the model's hands; tools connected through a common socket.
The question that remains is what to do with these parts.
Work that one tool call cannot finish — "research it, compare, then summarize", say — how do you hand over work like that?
