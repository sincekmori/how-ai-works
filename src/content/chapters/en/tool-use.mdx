The model can now answer in a fixed shape.
That power has a use pointing in an unexpected direction:
giving the model tools from the outside world.

## The limits of the model alone

However smart the model, some things are beyond it.
What it knows is only what it learned from the world's text, up to the moment it was trained.
So it does not know today's weather, or the current stock price.
And under the hood it is still, in the end, a contraption that picks each next word by probability.
Multiplying large numbers with a calculator's exactness is not its strength.

These are not weaknesses that more smartness would erase.
The latest information simply is not inside the model.
What's needed is not a better brain but the use of outside tools.
To learn the weather, ask a weather service; to compute, punch a calculator.
Humans do the same.

## And yet the model cannot operate a tool

Here lies a problem.
All the model can do, in the end, is emit words (tokens).
It cannot call a weather service over the network by itself, or press calculator keys.

This is where the previous chapter's structured output earns its keep.
Instead of operating tools, the model writes out a **tool call** — "use this tool, with these values" — in a fixed shape.
Wanting the weather, it emits something like:

```json
{ "tool": "get_weather", "city": "Tokyo", "when": "tomorrow" }
```

This is exactly the structured output of the last chapter.
Being fixed in shape, the program in between can read it reliably.
That program actually calls the weather service and hands the result back to the model.
The model reads the result and composes the final reply.
This round trip is **tool use** (also called **function calling**).

## The cast has grown to three

Every conversation in this book so far had two participants.
You (or a program) asked; the model answered.
However long the exchange, it was a world of requests and replies going back and forth.

With tools in the picture, a third character has joined the circle.
The weather service, the calculator, the search engine.
Something that is neither the model nor you has become a member of the exchange.

Tools, however, do not speak.
The model and the tool cannot talk to each other directly.
The program standing between them becomes the go-between:
it conveys the model's "call this tool" to the tool, and delivers the tool's result back to the model.
The three-way conversation always proceeds through the program in the middle.

The model's utterances now come in two kinds as well:
words meant for people, and calls meant for tools.
Your screen shows only the final reply.
But the behind-the-scenes transcript quietly holds lines you have never seen — the tool calls, and the results that came back.

## Walking the loop

Words alone make this hard to picture, so trace it step by step.

What matters is the division of labor.
The model only decides what to look up, and with which tool.
Actually running the tool is the in-between program's job.
The model takes the result and finishes it into a human-facing reply.
One thinks; the other does.

And tools go far beyond a weather service.
Web search, calculators, code execution, the company calendar, databases.
Anything callable in a fixed shape that returns a result can be a tool.
Most of the assistants you already use call tools behind the curtain in exactly this way.

## What happens as the tools multiply

Once you know tools can be handed over, appetite grows.
Weather, search, maps, calendars — why not all of them?
But wire each tool up by hand — "this one is called like this" — and with many models and many tools, hand-wiring every combination buries you in wires.
This wiring problem already has an answer waiting:
a common socket for the world of tools.
