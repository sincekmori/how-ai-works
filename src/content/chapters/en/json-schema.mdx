The JSON shape is in hand.
All that remains is getting the model to reply in it.
The most naive way: just ask, in the prompt (the instruction text handed to the model).

## Asking "reply in JSON"

For instance:

> Answer tomorrow's Tokyo weather as JSON shaped like `{ "city": ..., "condition": ..., "temperature": ... }`.

For simple shapes, the model usually plays along.
Choose "answer in a fixed shape (JSON)" in the demo below to watch.

Problem solved, one would like to say — but it is not that easy.
As Part I showed, the model picks word after word by plausibility.
"Reply in JSON" is a request, not a guarantee.
And indeed, it frays in the following ways.

## Requests alone fray

Fray number one: preambles.
The model, being helpful, tends to add one.

```text
Certainly! Here is tomorrow's weather for Tokyo:
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```

The opening sentence is not JSON, so the program cannot read the reply as-is.

Number two: fences.
Out of the habit of displaying code inside prose, wrappers like this appear:

````text
```json
{ "city": "Tokyo", "condition": "sunny", "temperature": 28 }
```
````

Number three: structural drift.
`temperature` meant as a number comes back as the string `"28 degrees"`, keys nobody asked for appear, or a key's name is subtly off.

You might think: extract the fenced part with a regex, then.
But remember the whack-a-mole of two chapters ago.
There is no guarantee a fence is present — and even with one, if the structure inside has drifted, it still cannot be read.
On a request basis, you never get past "probably fine".

## Defining the shape itself

So the idea moves up one more level.
Showing an example — "reply something like this" — is like showing a filled-in sample.
Instead, hand over a form whose blanks are fixed in advance.

Spell out that form's rules in words, and they read:

- The keys are exactly `city`, `condition`, and `temperature`
- The values of `city` and `condition` are strings
- The value of `temperature` is a number
- All three keys must always be present

One problem, though.
Handing these rules over as an English memo won't let machinery read them.
The rules themselves must be written in a fixed shape.

In what shape, then?
Look closely at the rules above: each is itself a key-and-value pair, like "the key `city` holds the kind: string".
And we already know the perfect shape for writing keys and values.
JSON.
So: write the rules for how JSON should be written — in JSON itself.
The world standard for writing such rules is **JSON Schema**.
A schema is a blueprint of a type.
The weather rules above, written as a JSON Schema:

```json
{
  "type": "object",
  "properties": {
    "city": { "type": "string" },
    "condition": { "type": "string" },
    "temperature": { "type": "number" }
  },
  "required": ["city", "condition", "temperature"]
}
```

Reading it works by the previous chapter's key-following.
`"type": "object"` says the whole is one `{ }` bundle.
Inside `"properties"` is which keys exist and what kind each value is.
`temperature` is `"type": "number"` — it must be a number (a string like `"28 degrees"` is not accepted).
`"required"` says these keys must be present.
This is not an example; it is a rule.
Not "roughly like this" but "no shape other than this is admitted".

## Why it holds, without fail

Hand over a schema through a call that actually enforces it, and the model keeps the shape — always.
Requests frayed; why can this be guaranteed?
The trick lies in "how the next word gets picked", from the inference chapter.

Each round, the model assigns probabilities to all candidates and picks one to append.
When a schema is present, a filter drops over that allocation table.
An allow-list is computed — "per the schema, only these pieces (tokens) may come next" — and every other candidate's probability is set to zero.

Say the model has written as far as `{ "city":`.
Per the schema, a string value must come next — an opening quote `"`.
So the choice is clamped: nothing but `"` can be picked.
When writing the value of `temperature`, only digits are selectable.
The model cannot insert a preamble, cannot add a fence, cannot misname a key.
Not guiding by request — carving the very corridor into the schema's shape.
That is why it holds without fail.
Output in a fixed shape like this is called **Structured Output**, with JSON Schema serving as the shape specification.
Two footnotes to "without fail".
The guarantee holds when the call uses the mode that actually applies this clamp (Structured Output).
And if the reply hits the max_tokens ceiling from the parameters chapter, even a correct shape can still be cut off midway.

## Now it's a component

It has been quite a road.
Trying to regex numbers out of free text, tiring of whack-a-mole, arriving at "have it reply in JSON", learning that asking is not enough — and finally defining and guaranteeing the shape itself.
The model's reply is now fixed-shape data that does not wobble.
Fixed-shape data can be read directly by a program and passed to the next step.
Chart the weather JSON, pass or fail by the score, hand the address to a maps service.
The model has gone from conversation partner to a component that connects with other components inside an app.

There is, by the way, a reverse use for this fixed-shape exchange.
What if the model were the one asking — "I'd like to use this tool, with these values" — in a fixed shape of its own?
