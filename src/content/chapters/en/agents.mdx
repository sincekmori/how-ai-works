The parts for putting the model to work are assembled:
structured output for fixed-shape answers, tools for reaching the outside world, MCP for connecting tools in a common shape.
This chapter combines them, and gives the model work that outgrows a single reply.

## Work that doesn't finish in one round

Tool use so far was, in effect, one round trip.
The model calls a tool once, reads the result, answers.
Real-world tasks are rarely that simple.

Take: "I want to walk at the warmest hour in Tokyo tomorrow. When?"
Answering requires stages — look up the temperature by hour, find the warmest hour, then check whether it will rain at that hour.
Moreover, what is learned along the way (3 p.m. is warmest) determines what to check next (rain at 3 p.m.).
Not a straight road: read the result, then choose the next move.

## Run the loop

So the single round trip becomes a repeat.
The whole recipe:

**Think → use a tool → read the result → think again.**

Keep the loop running until the goal is reached.
That is an **agent**.

<AgentLoop lang="en" />

What separates this from an ordinary model is not the number of rounds but deciding the next move itself.
What to look up, which tool comes next, whether enough is known —
the model judges these as it goes, looking at intermediate results.
It plans, keeps track of progress, switches between tools, and heads for the goal.

## Not all smooth sailing, though

Up to here, it sounds as if a spinning loop could do anything.
Build an agent for real, and new troubles line up quickly.
Problems that stayed small in a single round snowball inside a repeat.

First, agents lose their way.
As Part I showed, the model picks words probabilistically, so now and then it picks a strange move.
In ordinary chat, a strange reply just meant you asked again.
Inside a loop, the next move gets stacked on top of the mistaken one.
A small early stumble is a major detour ten moves later.

Second, they go in circles.
Look it up, fail to understand, look up the same thing again — agents do fall into that ring.
This is why real agents almost always carry a cap: "at most N moves."
When it hits the cap, it shows a human its progress so far and asks for direction.
Never letting it run forever is the most basic safety device.

Third, time and money.
The loop calls the model every turn; dozens of turns make replies slow and bills fat.
How far it may investigate alone, where it must wrap up —
that line, too, is for the builder to draw in advance.

And the scariest: the irreversible move.
With look-things-up tools, failure costs a redo.
But hand over "send an email", "buy something", "delete a file"?
A wrong move now changes the real world.
So the design pauses before important operations and checks with a human.
Skill in agent building shows less in making the loop spin than in making it stoppable, safely.

## After the loop: teaching

The agent now works.
Use one daily, though, and something becomes obvious fast.
The agent is smart, yet it knows nothing of how things are done at your job.
And every new conversation resets whatever you had explained.
This "what I taught doesn't survive to the next conversation" problem — how does it get solved?
