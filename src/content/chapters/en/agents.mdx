By now the parts for "using" a model are on the table.
**Structured output** to answer in a fixed shape, **tools** to call the outside world, **MCP** to connect tools in a common shape.
This chapter combines them to have the model do a **job that goes beyond a single reply**.

## A job that isn't done in one turn

Tool use so far was, in effect, "one round trip."
The model calls a tool once, reads the result, and answers.
But real jobs aren't that simple.

Take "I want to walk at the warmest hour in Tokyo tomorrow — when?"
Answering that means first getting the temperature by hour, finding the warmest one, then checking it won't rain at that hour, and so on — **several stages**.
And what you learn along the way (15:00 is warm) decides what to check next (rain at 15:00).
It's not a straight line; you **read the result and decide the next move**.

## Run the loop

So we turn the tool's "one round trip" into a **repeat**.
That's all it is:

**Think → use a tool → read the result → think again.**

Keep looping until the goal is met.
That is an **agent**.

<AgentLoop lang="en" />

The difference from an ordinary model isn't "how many times" but "**deciding the next step itself**."
What to look up, which tool to use next, whether it has enough — the model judges as it goes, reading the results in between.
It plans, remembers the progress, uses different tools, and heads for the goal.

When an assistant you use looks things up, follows steps, and gets a longer task done, this loop is usually turning behind the scenes.

## It isn't all smooth sailing, though

Hearing all this, it sounds like the loop can do anything.
But actually build an agent, and new struggles arrive one after another.
Problems that were small in a single turn **snowball** inside a loop.

First, it **wanders off the path**.
As Part I showed, a model picks words by probability, so now and then it picks a strange move.
In ordinary chat, a strange reply costs little — you just ask again.
Inside a loop, though, the next move is stacked **on top of** the wrong one.
A small early stumble is a big miss ten moves later.

Second, it **goes in circles**.
It can fall into the loop of "look it up → still unclear → look up the same thing again."
That's why real agents almost always carry a **cap on the number of moves** — "at most N steps."
Hit the cap, show a person the progress so far, and ask for directions.
Never letting it run forever is the most basic guardrail.

Then there's **time and money**.
The loop calls the model once per turn.
Run dozens of turns and replies get slow, and the bill grows.
How far it should dig on its own, and where it should cut its losses — that line, too, is for the builder to draw.

Scariest of all is the **irreversible move**.
With look-things-up tools, a failure just means retrying.
But hand it tools that "send an email," "buy something," "delete a file"?
A wrong move now changes the real world.
So before the moves that matter, the design makes it **stop and ask a human first**.
The craft of building agents shows less in making the loop run than in **making the loop safe to stop**.

## Next: after the loop, the teaching

The agent runs now.
But use one every day, and you soon notice something.
It is smart, yet it doesn't know "how we do things here" — your way of working.
And every new conversation resets your careful explanation to square one.
The final chapter looks at **Agent Skills**, the mechanism for teaching an agent your procedures — and closes the book.

## Summary

- An **agent** is the loop "think → use a tool → read the result → think again," run until the goal is met.
- No new part was added; it's structured output and tools, simply **repeated**.
- The difference isn't the count but "**deciding the next move yourself, from the results so far**."
- Loops come with struggles — wandering, circles, time and money, irreversible moves. So they ship with **guardrails**: step caps and asking a human.
- With it, the model can take on multi-step jobs that go beyond a single reply.
