The opening chapter of this part showed that inside an app, the thing receiving the model's reply is a **program**.
And that a program is worst at free-form text.
But how bad is it, really?
Let's find out by getting our hands dirty.
That difficulty is the starting point for an important idea coming up.

## First, the naive attempt

Say the model replies:

> Tokyo tomorrow: up to 28C.

Why would we want to dig a number out at all?
Say we're building an app like this: if tomorrow looks like it will top 30°C, it sends a morning notification — "heat warning, drink plenty of water."
To decide whether to send it, the program has to make a **numeric comparison**: is tomorrow's temperature greater than 30?
The sentence "up to 28C" can't be compared with 30.
Only a number can.
That's why we want to pull just the **temperature number (28)** out of this reply.
A program doesn't understand the sentence, but it can hunt through the characters for a pattern.
That kind of pattern search is done with a **regular expression** (regex).
A regex is a little notation for saying "find a string shaped like this."
For example, `\d` means "one digit," and `\d+` means "a run of one or more digits."
You don't need to learn to read or write these symbols here — not at all.
Knowing "there's a tool like this that searches for a character pattern" is all this chapter asks.

For that sentence, `\d+` grabs "28."
It worked.
…Did it, though?

## As the wording changes, it crumbles

The trouble is that the model's reply **isn't worded the same way every time**.
In the demo below, pick a regex and see what it grabs from each of the three sentences.

<RegexTrap lang="en" client:visible />

Try it, and here's what happens.

- `\d+` (the first number) grabs the **date, 3**, in "On the 3rd, Tokyo goes up to 28C."
- So you try `up to \d\dC`, which dodges the date. But "the temperature is 28C" is worded without "up to," so it **doesn't match**.
- So you add `temperature is \d\dC`, and now the "up to 28C" sentences slip through.

**Whichever pattern you pick, none gets all three sentences right.**
Every new wording you think of means bolting on another regex.
What about "15C in the morning, 28C at noon"? What if it's "28°C" with a different unit? What if it's spelled "twenty-eight"?
There's no end to it.
This is endless **whack-a-mole**.

## Flip it around

Here's the key realization.
All along, we were trying to pull data out of a free-form sentence **that was already written**.
That's why we got stuck chasing an infinity of wordings.

So what if we flip it?
**Have it written, from the start, in a shape that's easy to pull from.**
Instead of "answer in a sentence," ask the model to "answer in this shape."
As it happens, such an easy-to-pull-from shape is already used the world over.
It's called **JSON**.

If the reply were

```json
{ "temperature": 28 }
```

then whack-a-mole is over.
You just take the value at the key `temperature`, and you reliably get 28, every time.
The wordings are infinite, but the **shape can be pinned to one**.
