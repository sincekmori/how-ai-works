Inside an app, the model's reply is received by a program, and a program is worst at free-form text.
How bad is it, exactly?
Let's find out hands-on.

## The naive first attempt

Say the model replies:

> Tokyo tomorrow: up to 28C.

Why dig a number out at all?
Suppose we are building this app: if tomorrow looks like it will top 30°C, it sends a morning notification — "heat warning, drink plenty of water."
To decide whether to send it, the program must make a numeric comparison: is tomorrow's temperature greater than 30?
The sentence "up to 28C" cannot be compared with 30.
Only a number can.
That is why we want just the temperature number (28) out of this reply.

A program does not understand the sentence, but it can hunt through the characters for a pattern.
Pattern searches like "find a run of digits" are done with a **regular expression** (regex) — a small notation for saying "find a string shaped like this."
For example, `\d` means one digit, and `\d+` means a run of one or more digits.
There is no need to learn to read or write these symbols here.
Knowing that a tool exists for searching by character pattern is all this chapter asks.

For that sentence, `\d+` grabs "28".
It worked.
Did it, though?

## As the wording changes, it crumbles

The trouble is that the model's reply is not worded the same way every time.
In the demo below, pick a regex and see what it grabs from each of the three sentences.

<RegexTrap lang="en" client:visible />

Try it, and this is what happens.

- `\d+` (the first number) grabs the date, 3, in "On the 3rd, Tokyo goes up to 28C."
- So you try `up to \d\dC`, which dodges the date. But "the temperature is 28C" is worded without "up to", so it doesn't match.
- So you add `temperature is \d\dC` — and now the "up to 28C" sentences slip through.

Whichever pattern you pick, none gets all three sentences right.
Every new wording you think of means bolting on another regex.
What about "15C in the morning, 28C at noon"?
What if it is written "28°C", with the degree sign?
What if it is spelled out, "twenty-eight"?
There is no end.
It is whack-a-mole, forever.

## Flip it around

Here is the thing worth noticing.
All along, we have been trying to extract information after the fact, from free text that was already written.
That is why we ended up chasing an infinity of wordings.

What if we flipped it?
Have the reply written in an easy-to-extract shape from the very start.
Change the request from "answer in prose" to "answer in this shape."
Such easy-to-extract shapes already exist, in use all over the world.
The name of one is **JSON**.

If the reply were

```json
{ "temperature": 28 }
```

the whack-a-mole would be over.
Read the value under the key `temperature`, and 28 arrives reliably, every time.
Wordings are infinite, but the shape can be fixed to one.

So what kind of shape is this JSON, exactly?
